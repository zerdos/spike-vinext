1. EXECUTIVE SUMMARY & VISION
================================================================================
As AI coding agents (Claude Code, Cursor, Windsurf, Roo Code, custom LangChain/
LlamaIndex swarms) integrate dozens of external capabilities, providing all tool 
definitions upfront catastrophically bloats the LLM context window. Providing 
hundreds of tool schemas wastes 30k-100k+ tokens on every single turn, causes 
hallucinations, increases latency, and quickly hits context window limits.

The Spike Land MVP delivers a lean, high-performance edge-native MCP Gateway that 
solves this via **Progressive Context Disclosure**:
1. Agents connect and see only **5 minimal Gateway Meta-Tools** (< 1.5k tokens).
2. Agents discover tools on-demand via keywords or semantic task intent.
3. Relevant schemas and categories are dynamically activated into the session 
   without restarting or reconfiguring the client.
4. Agents can search, inspect, and mount third-party MCP servers from global 
   ecosystem registries (Smithery, Glama, Official MCP Registry) directly through 
   the gateway.

This turns Spike Land into the default tool router for AI agents—fast, context-
efficient, and capable of scaling from 5 tools to 1,000+ without degrading agent 
intelligence.

2. PROBLEM STATEMENT & BACKGROUND
================================================================================
Current MCP client configurations (e.g., in `.cursor/mcp.json` or 
`claude_desktop_config.json`) require loading every configured server's entire 
schema definition at initialization:

1. **Context Window Exhaustion:**
   - Loading 50-100 typical MCP tools consumes between 25,000 and 70,000 tokens of 
     system prompt overhead on EVERY prompt/completion cycle.
2. **Model Confusion & Tool Selection Degradation:**
   - When models are presented with 50+ tools with overlapping descriptions, 
     tool call accuracy drops precipitously; models frequently hallucinate 
     parameters or invoke incorrect tools.
3. **Fragmented Server Ecosystem:**
   - Discovering, verifying, and configuring third-party MCP servers (from GitHub, 
     Smithery, Glama, Docker) requires tedious manual editing of config files, 
     API keys, and local environment variables.
4. **Edge Latency & Multi-Device Synchronization:**
   - Local STDIO servers fail in cloud-hosted, mobile, or multi-agent environments. 
     A unified, globally distributed HTTP/SSE edge proxy is required.

3. MVP SCOPE, NON-GOALS & CORE HYPOTHESES
================================================================================

3.1 In-Scope for MVP
- **Edge MCP Server (`/api/mcp` and `/api/mcp/sse`):**
  A standard JSON-RPC 2.0 MCP server implementing tools/list, tools/call, 
  and progressive disclosure.
- **5 Gateway Meta-Tools:**
  `search_tools`, `list_categories`, `enable_category`, `get_balance`, `get_status`.
- **Progressive Tool Registry:**
  Curated catalogue of tool categories (starting with Development, AI & Creative, 
  Filesystem, Web & HTTP, and Registry management).
- **MCP Registry Search & Install:**
  Querying external registries (Smithery, Glama, Official), inspecting schemas, 
  and exporting `.mcp.json` configurations or proxying calls.
- **Interactive Web Interface:**
  A web playground for developers to test progressive disclosure, execute mock 
  or live tool runs, and copy 1-click configuration snippets for Claude, Cursor, 
  and Claude Code.

3.2 Non-Goals for MVP (Deferred to v2)
- Complex multi-agent peer-to-peer swarms (AI Orchestrator swarm tools).
- Heavyweight full-stack app generation pipelines (`/create` autonomous app generation).
- Social media autopilot scheduling & Ad Allocator integrations (Orbit legacy suite).
- Native desktop binary clients (web browser + standard MCP clients only).
- Billing paywalls & Stripe metering (mock/free quota in MVP).

3.3 Core Hypotheses
- **H1:** Progressive disclosure reduces agent initial token consumption by > 90% 
  compared to static tool catalogues.
- **H2:** Developers can connect an external client (Claude Desktop / Cursor) in 
  < 60 seconds using the generated configuration snippet.
- **H3:** Agents can discover and call an unlisted tool via `search_tools` in a 
  single autonomous turn without human intervention.

- **Journey 1: Zero-Config Client Connection**
  Alex visits `/mcp`, selects "Cursor", copies the one-line `.cursor/mcp.json`

  5 gateway tools.
- **Journey 2: Dynamic Tool Discovery During Coding**
  Alex asks Claude: "Scrape this documentation site and summarize it." Claude 
  has no scraping tool loaded. It calls `search_tools("scrape web page")`, 
  receives `scrape_page` with its schema, calls it, and completes the task.
- **Journey 3: Discovering Third-Party Server from Registry**
  Jordan asks Claude: "Find a GitHub MCP server to check PR issues." Claude calls 
  `mcp_registry_search("github pull request")`, inspects the configuration, and 
  returns the setup command.

6. FEATURE SPEC: PROGRESSIVELY DISCLOSED MCP SERVER
================================================================================

6.1 Gateway Handshake & Bootstrap
When any MCP client connects and issues `initialize` followed by `tools/list`, 
the server MUST return ONLY the 5 Gateway Meta-Tools.

Gateway Tool Definitions:
1. **`search_tools`**
   - *Description:* "Search across all 455 tools by semantic query or keyword with progressive schema loading."
   - *Parameters:*
     - `query` (string, required): Search query or task intent (e.g. "resize image", "git commit").
     - `category` (string, optional): Specific category filter.
     - `limit` (number, optional, default: 5): Maximum tools to return.
   - *Returns:* Matched tools with schema definitions, category, and relevance score. Automatically adds matched tools to the active session context.

2. **`list_categories`**
   - *Description:* "List all available tool categories with descriptions, tool counts, and activation status."
   - *Parameters:*
     - `enabledOnly` (boolean, optional, default: false): Filter to only active categories.
   - *Returns:* Array of categories with metadata (`id`, `name`, `toolCount`, `isEnabled`, `icon`, `description`).

3. **`enable_category`**
   - *Description:* "Dynamically mount all schemas and endpoints for a specific category into active session context."
   - *Parameters:*
     - `category` (string, required): Category ID or exact name.
   - *Returns:* Confirmation message, count of newly exposed tools, and list of tool names.

4. **`get_balance`**
   - *Description:* "Check current API token/credit balance, usage limits, and tier status."
   - *Parameters:* None.
   - *Returns:* Object containing `balance`, `currency`, `tier`, `monthlyQuotaRemaining`, `rateLimit`.

5. **`get_status`**
   - *Description:* "Retrieve health, edge region, latency, and available feature status."
   - *Parameters:* None.
   - *Returns:* Object with server version, edge datacenter (e.g., LHR, SFO), active categories, and total available tools count.

6.2 Dynamic Tool Resolution & Schema Hydration
- **Session-Based Tool Scope:**
  - Each connection (identified by SSE session ID or client Authorization header) 
    maintains an active tool table in memory / Cloudflare KV.
  - Initial state: `[search_tools, list_categories, enable_category, get_balance, get_status]`.
- **Search-Triggered Hydration:**
  - When `search_tools` is called, any matched tools are temporarily registered into 
    the active session's tool table.
  - The tool returns the full JSON Schema of the matching tools so the LLM can 
    immediately call them in the next turn.
- **Category-Triggered Hydration:**
  - Calling `enable_category("AI & Creative")` expands the active tool table with all 
    60 tools in that category.
  - If supported by the transport, the server triggers an MCP protocol notification:
    `notifications/tools/list_changed` to alert the client to re-request `tools/list`.

6.3 Execution & Fallback Handlers
- When `tools/call` is executed for a tool:
  - If tool is already activated in session -> execute handler immediately.
  - If tool is valid in the platform catalogue but NOT yet explicitly enabled -> 
    Auto-hydrate: dynamically execute the tool and return its result along with a 
    system notice: `"[Info: Tool 'foo' was auto-mounted into active session context]"`.
  - If tool does not exist -> return standard JSON-RPC error `-32601` ("Method/tool not found") 
    with a helpful hint: `"Tool not found. Use search_tools to discover available capabilities."`

7. FEATURE SPEC: MULTI-REGISTRY MCP INTEGRATION
================================================================================

The MCP Registry module allows AI agents to act as autonomous tooling architects: 
finding, vetting, and installing tools from the broader MCP ecosystem.

7.1 Aggregated Registry Search
Expose the following MCP tools under the `mcp-registry` category:

1. **`mcp_registry_search`**
   - *Description:* "Search across Smithery, Official MCP Registry, and Glama for MCP servers by keyword."
   - *Parameters:*
     - `query` (string, required): Keywords (e.g. "postgres", "brave search", "slack").
     - `registry` (enum: `all`, `official`, `smithery`, `glama`, optional, default: `all`).
     - `limit` (number, optional, default: 10).
   - *Returns:* List of servers containing:
     - `id`: Unique identifier (e.g., `@smithery/sqlite` or `modelcontextprotocol/server-postgres`).
     - `name`: Human-readable title.
     - `description`: Server capability overview.
     - `registrySource`: `official` | `smithery` | `glama`.
     - `downloads` / `stars` / `verifiedStatus`.
     - `transportType`: `stdio` | `sse` | `http`.

2. **`mcp_registry_get`**
   - *Description:* "Get detailed information about a specific MCP server including connection configuration, required environment variables, and tool list."
   - *Parameters:*
     - `serverId` (string, required): The ID returned from registry search.
   - *Returns:*
     - Full README / manifest.
     - Environment variable requirements (`env`: e.g. `GITHUB_TOKEN`, `DATABASE_URL`).
     - Available tools inside the package.
     - Sample configuration snippet for Cursor / Claude Desktop.

3. **`mcp_registry_install`**
   - *Description:* "Generate auto-configured client snippet or mount an MCP server via proxy."
   - *Parameters:*
     - `serverId` (string, required).
     - `clientType` (enum: `cursor`, `claude_desktop`, `claude_code`, `http`, default: `cursor`).
     - `envVariables` (record<string, string>, optional).
   - *Returns:*
     - Ready-to-copy JSON block to insert into `.mcp.json` or `claude_desktop_config.json`.
     - Direct proxy URL if hosted through Spike Land.

4. **`mcp_registry_list_installed`**
   - *Description:* "List all currently configured or proxy-mounted MCP servers in the current workspace."
   - *Parameters:* None.
   - *Returns:* Active server list with connection status and latency.

7.2 Registry Caching & Fallbacks
- Cache registry search results in edge KV with a 1-hour TTL.
- If upstream registry (e.g., Smithery API) is rate-limited or down, fallback to 
  the cached Official MCP GitHub catalogue snapshot.

9. SECURITY, AUTHENTICATION & PERMISSIONS
================================================================================

9.1 Authentication
- **Anonymous Tier:**
  - Open access to the 5 Gateway tools and read-only search across platform tools 
    and MCP registries.
  - Rate limit: 60 requests/minute per IP.
- **Bearer API Key Tier:**
  - Authenticated requests pass `Authorization: Bearer sk_spike_...` in HTTP headers.
  - Keys can be created at `/settings` or programmatically via `settings_create_api_key`.
  - Keys are masked after initial display (`sk_spike_****...****`).
  - Rate limit: 600 requests/minute.

9.2 Tool Execution Sandboxing
- High-risk operations (file writes, code evaluation, external HTTP webhooks) MUST 
  be validated against permissions:
  - Read-only tools (`search_tools`, `get_status`, `learnit_get_topic`) require no special approval.
  - Mutating tools (`filesystem_write`, `deploy_project`) require explicit client-side 
    approval or workspace elevated tokens.
- Secret isolation: Keys passed to registry tools are NEVER echoed back in logs or tool results.

10. PROTOCOL & API INTERFACE SPECIFICATIONS
================================================================================

10.1 MCP Transport Endpoints
- **Streamable HTTP POST Endpoint:** `/api/mcp`
  - Accepts standard JSON-RPC 2.0 requests.
  - Headers: `Content-Type: application/json`.
- **Server-Sent Events (SSE) Endpoint:** `/api/mcp/sse`
  - Long-lived connection for bi-directional messaging and dynamic notifications.
  - `GET /api/mcp/sse` establishes stream; returns `endpoint` event containing message POST URI.

10.2 JSON-RPC 2.0 Method Payloads

**Request 1: `initialize`**
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2024-11-05",
    "capabilities": {
      "tools": { "listChanged": true }
    },
    "clientInfo": { "name": "Cursor", "version": "0.45.0" }
  }
}
```

**Response 1: `initialize`**
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2024-11-05",
    "capabilities": {
      "tools": { "listChanged": true }
    },
    "serverInfo": {
      "name": "spike-land-gateway",
      "version": "1.0.0-mvp"
    }
  }
}
```

```json

// Core Tool Types (TypeScript / Zod)
export interface ToolParameter {
  type: "string" | "number" | "boolean" | "object" | "array";
  description: string;
  required?: boolean;
  enum?: string[];
  default?: unknown;
}

export interface ToolDefinition {
  name: string;
  description: string;
  category: string;
  tier: "free" | "workspace";
  inputSchema: {
    type: "object";
    properties: Record<string, ToolParameter>;
    required?: string[];
  };
  handler?: (args: Record<string, unknown>, ctx: RequestContext) => Promise<unknown>;

export interface CategoryDefinition {
  id: string;
  name: string;
  count: number;
  icon: string;
  description: string;
  tools: ToolDefinition[];
}

// Registry Search Result
export interface RegistryServerRecord {
  id: string;
  name: string;
  description: string;
  homepage?: string;
  repository?: string;
  registrySource: "official" | "smithery" | "glama";
  transport: "stdio" | "sse" | "http";
  installCount?: number;
  tags: string[];
  configTemplate: Record<string, unknown>;
}

// Session State in Edge KV
export interface MCPSessionState {
  sessionId: string;
  createdAt: number;
  lastActiveAt: number;
  activatedCategories: string[];
  activatedTools: string[]; // Dynamically hydrated tools
  clientInfo?: { name: string; version: string };
}
```

15. RISKS, MITIGATIONS & OPEN QUESTIONS
================================================================================
- **Risk 1: Client Doesn't Support `notifications/tools/list_changed`:**
  - *Mitigation:* The Gateway supports *Auto-Hydration*. If an agent infers a tool name from `search_tools` and immediately calls it via `tools/call` without re-requesting `tools/list`, the server automatically recognizes and executes it.
- **Risk 2: Rate Limiting on External Registries (Smithery/Glama):**
  - *Mitigation:* Maintain a bundled static fallback registry manifest deployed directly within the worker bundle.
- **Open Question 1:** Should third-party MCP servers discovered in the registry be proxied through Cloudflare Workers (hosted SSE proxy) or strictly configured for client-side STDIO?
  - *MVP Decision:* Return client-side configuration blocks for STDIO; offer hosted proxy for public HTTP/SSE endpoints.
